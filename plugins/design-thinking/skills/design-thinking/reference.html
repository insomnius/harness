THE NOTATION

A ticket names a behavior. The code is a graph.

The work is finding which nodes the behavior touches, proving it, changing them in the right order, and keeping the map honest as it changes underneath you.

   X   →   Y   →   Z
   │       │       │
   │       │       └─ what Y calls          downstream
   │       └───────── the node in hand
   └───────────────── what calls Y          upstream
           │
           ├─ A  what flows through on success
           ├─ E  where it breaks, and what happens then
           └─ R  what it needs to exist

A node is a file with one purpose; a symbol inside it; a behavior inside that. An edge is a call, an import, an invocation, a request, a publish, shared state, or a provisioning relationship. The graph does not stop at the process boundary.

01 · WORK IS A LOOP

Not a pipeline. One turn takes one natural-language requirement and ends when an automated check says it is satisfied.

        natural language requirement
                    │
   ┌────────────────▼────────────────┐
   │ DECIPHER   prose → graph delta   │  requirements · language
   │                                 │  keyword · locate · trace
   │                                 │  cross · triage · order
   └────────────────┬────────────────┘
   ┌────────────────▼────────────────┐
   │ SPECIFY    done, made runnable   │  acceptance  red  requirement
   │                                 │  channels+test red behavior
   └────────────────┬────────────────┘
   ┌────────────────▼────────────────┐
   │ GATE       ten checks, blocking │
   └────────────────┬────────────────┘
   ┌────────────────▼────────────────┐
   │ CHANGE     passes, then retrace  │
   └────────────────┬────────────────┘
   ┌────────────────▼────────────────┐
   │ CLOSE      unit → contract → e2e │  green closes it
   │                                 │  red routes back
   └────────────────┬────────────────┘
                    │
      next requirement, warmer glossary

Closure is observed, not asserted. A requirement is closed when a check that was red before any code went green on its own — never because the work looks done. An agent judging its own output is the weakest evidence available, and replacing that judgment is the point of the loop.

Reading the close

unitcontractacceptmeans
✓ pass✓ pass✓ passclosed, with the red→green transition recorded
✓ pass✓ pass✗ redbehaviors right, requirement unmet — the most informative failure in the method
✓ pass✗ red✗ redthe seam is wrong → cross
✗ red— n/a✗ reda behavior is wrong → implement
✓ pass✓ pass⚠ on retrynot green. Fix the check's determinism

Row two routes two ways, and guessing is expensive. Either the graph delta missed a node — back to trace, with the acceptance failure as the new seed — or the requirement was misunderstood at translation time, and no amount of implementation fixes that. Read the expected-versus-observed diff before choosing. Guessing here produces the worst outcome available: correct code, wrong feature, everything green except the one check that mattered.

Two things that keep the loop honest

Ambiguities become assertions. Every assumed expectation in the ambiguity register gets an assertion in the acceptance check. When one fails, the assumption was wrong — that is a requirement finding to report, not a bug to quietly fix, and it catches a misunderstanding before it ships.

Stop rather than grind. Halt on the first turn with the acceptance check still red that produces no new failure, node, behavior, falsified assumption, resolved unsure, or new diagnosis of the same failure; report the diff, what was tried each turn, and the likeliest misreading of the requirement, then ask.

02 · THE TWO HARD RULES

Everything else in the skill is tunable guidance. These are constraints.

REQUIREMENT GATE

No work on a requirement until an automated check for it exists and is red for the intended reason.

BEHAVIOR GATE

No code for a behavior until its contract is annotated and its test is red for the intended reason.

Same discipline at two altitudes. The behavior gate stops you writing unspecified code; the requirement gate stops you writing code toward an undefined outcome. Both are recorded in a ledger, so a resumed session cannot skip them — a behavior with implementation started and no ledger entry is a violation, not a state to continue from.

Red for the intended reason is the check that does the work and the one most easily faked. An assertion failure describing the missing behavior counts. A resolution error naming precisely the symbol about to be written counts — that is legitimate first-step red in a typed language. A broken harness, a missing fixture, or a failure inherited from someone else's commit does not. Know what was already red before you started.

The gate refuses to be talked past. An agent that can be argued into skipping it does not have a gate.

03 · FIVE TIERS

2fflow — end-to-end pathF1trace.json

Tier 4 is where the method operates. You do not change a file, you change a behavior. Requirements are satisfied by behaviors; behaviors are proven by tests. That chain is the only accepted evidence of done — which also means a requirement with no behaviors is not implemented, however much code was written.

Tier 2 exists for addressing and drift detection. Tiers 0 and 1 are shared across a ticket, so each task gets its own trace file rather than re-reading the whole ticket's graph every turn.

The phase set is computed, not chosen

There are no lanes. Each phase carries a predicate over the change itself: cross runs only when a seam is on the path, order only when more than one node changes, channels annotates only the delta for a body-only change, language degenerates to a lookup when every term already resolves. So a one-line fix runs a handful of phases and a cross-service migration runs all eighteen, with nobody picking a mode — the picking is where judgement leaks out. Skipped phases are stated once in the first status tree, since a phase silently not run is indistinguishable from one forgotten.

Both gates are exempt. On a one-line fix they cost one red test and one contract annotation; skipping them saves minutes and forfeits the method.

The loop-back edges matter as much as the forward ones

  • A failing test on a node marked unaffected means the trace was wrong, not the test. That inversion makes the test suite the validator of the analysis.
  • A behavior discovered during implementation returns through annotation, test and gate before any code is written for it.
  • Reality contradicting the model sends you back to the model, not around it.
  • Resolving an unsure that reveals a new dependency reopens the trace.

WHERE EXPANSION STOPS

outcomemeaning
✓ ABSORBEDthe neighbour's contract is unchanged. The normal stop — record the invariant that must hold
⊗ MISPLACEDthe change reaches here but this node's purpose does not cover it. Route it; do not absorb it
⇉ CROSSINGa seam. Not a stop — keep tracing with different mechanics
▪ OPAQUEgenuinely unreachable: third party, vendored binary, no access. Rarer than it looks
✓ COMPLETE_UPthe flow's entrypoint is reached. Upstream is finished by construction, not by a hop count
✓ COMPLETE_DOWNa leaf, or a seam whose far side is opaque
▪ PASS_THROUGHthree hops that transform nothing — a delegation chain. Collapse to its two ends and continue from the far one
⚠ NO_ABSORPTIONstill propagating at the entrypoint, so nothing absorbed it. A finding, not a stop: re-seed, or report that the path has no absorption point

Depth is not the stop condition; absorption is. Keep expanding while the change's effect reaches the neighbour, and stop at the node that swallows it or at a structural end.

Caller count decides nothing — compatibility does. Forty-seven callers of a shared type cost nothing when the delta is additive, so upstream is not expanded at all. One caller costs a migration when it is breaking, and then the set is enumerated exhaustively: with a compiler where there is one, with a coverage run where there is not. If neither is available, the contract is not broken in place — the new shape is added beside the old and migrated under observation.

EVIDENCE HAS TIERS, LANGUAGES DO NOT HAVE MOODS

tiersourcegives
1compilerthe exhaustive caller set, including interface dispatch
2coveragethe empirical caller set — strongest evidence with no compiler
3referencesstatic references, usually missing dynamic dispatch
4textidentifiers and strings; the only tier that finds routes and name-based registration
5reasoningabout DI, reflection, metaprogramming, framework registration

Those five names are canonical — they are the values design.py --evidence accepts, and a hedged variant of one is not a tier at all.

A contract-changing symbol needs tier 1 or 2; anything weaker is unsure, and unsure must be resolved before the gate — which is what actually forces the coverage run to happen. A dynamic language is not condemned to guessing, it is condemned to running its tests.

05 · FORTY-THREE PRINCIPLES

Forty-three statements: thirty-one numbered, plus twelve lettered refinements that sharpen a parent rather than stand alone. The method, with no tools in it. Everything else in the skill illustrates one of these in some stack. When a recipe conflicts with a principle, the principle wins. When a stack is not covered, ask the principle's question and find that stack's answer — a language with no compiler still has dependencies, they just get written down instead of proven.

WORK

  1. Work is a loop.Natural language in, a graph delta in the middle, a green automated check out.
  2. Closure is observed, not asserted.Done means a check that was red went green on its own.
  3. Stop rather than grind.Report the pattern across failures instead of attempting a fourth time.

THE GRAPH

  1. The graph already exists.Discover it; do not invent it. Code, tests, table names and commit history hold the model already.
  2. Nodes and edges.File, symbol, behavior. Calls, imports, invocations, requests, publishes, shared state, provisioning.
  3. Trace both directions.Up to callers, down to callees, stopping at absorption.
  4. Count decides nothing; compatibility does.Many callers cost nothing when the delta is additive; one costs a migration when it is breaking.
  5. Evidence has tiers.compiler, coverage, references, text, reasoning. A contract change needs one of the top two; weaker is unsure.
  6. Reachable is not the same as belongs.A change reaching a node whose purpose does not cover it is misplaced.
  7. Deletion is a delta.Removing a node, a dead alias or a displaced rule is a change like any other, and gets traced like one.
  8. Behavior is the unit.Requirements are satisfied by behaviors; behaviors are proven by tests.
  9. The behavior statement and the test name are the same sentence.If they differ, one of the two is describing something nobody asked for.
  10. The code is the graph.A mismatch means the implementation is wrong, not the graph.
  11. A belongs to a flow.The success path is a property of the end-to-end path; a node's A is its slice of the flow's A.

EVERY NODE

  1. Three channels.What flows, where it breaks, what it needs — annotated before the node is written.
  2. The success path reads alone.If following it means stepping over retries and catches, they are tangled.
  3. Errors are named values with one policy each.Retry with a bound, fall back with a stated loss, propagate in this layer's words, or die.
  4. Dependencies are explicit.An ambient dependency is invisible in the signature and is why a node cannot be tested.
  5. Dependencies point inward.The domain depends on nothing; adapters depend on the domain, never the reverse.
  6. Parse once, at the edge.Trust nothing at the boundary and everything inside it.
  7. Make illegal states unrepresentable.Push validity into the type where the language allows it, so the invalid case cannot be constructed.
  8. Cleanup is structural.If an early return or a cancellation can skip it, the resource is not scoped.
  9. Substitutability is a design property.Needing to fake the world to test one node means the node does too much.

MEANING

  1. Translate before searching.The code usually speaks an older dialect than the ticket, so search the dead names too.
  2. Investment follows subdomain.Core gets the model; supporting and generic get the shortest thing that works.
  3. One term, one meaning, one context.Two names for a concept is debt. One name for two concepts is a bug waiting.
  4. Invariants and sequences live in different places.A rule with nowhere to live means a concept has no name yet.
  5. Consistency has a boundary.Two boundaries changing atomically means the boundary is wrong, or it is a policy.

BOUNDARIES BETWEEN SYSTEMS

  1. A seam is a node.It has a contract, and it can drift while both sides' code stays still.
  2. Crossing translates.Errors most of all. That mapping is where two systems' bugs live.
  3. Completeness is unavailable across a published seam.Compatibility replaces it.
  4. What cannot be enumerated can be observed.Replace "who calls this" with a measurement of who actually does.
  5. Relationship predicts blast radius.Knowable before tracing, from how the two systems relate.
  6. Rollout is bidirectional.Old callers against the new provider, and new callers against the old one.

DISCIPLINE

  1. Specify before building, at both altitudes.These two are the constraints; the rest is guidance.
  2. Red for the intended reason.Know what was already failing before you started.
  3. Discovery during implementation is information, not friction.It returns through annotation, test and gate.
  4. A trace is valid only at the commit it was taken against.Others commit; providers deploy.
  5. The trace is the memory; context is a cache.A verdict or a purpose not written down is lost at the next compaction.
  6. Log the decision, not the state.State is a fold over decisions, so a reversal keeps the reason that moved it.
  7. A failing test on a node you marked unaffected means the trace was wrong.Not the test.
  8. Report as a graph.Prose explains the graph; it does not replace it.
  9. One source of truth; every view is rendered.The state files are derived, never hand-edited, so the views cannot disagree.

06 · A, E, R

Annotate the flow's A first, then each node's three channels in this order: shapes → A → cardinality → E → R → boundary → layers → scope. The order is load-bearing. Doing E before A is how a happy path becomes unreadable.

Shapes come first

You cannot draw the graph until you know what flows through it.

shapeiswhy
recordan entity that flowsnames the thing, in the domain's words
ididentity, constraineda bare string accepts every other string
variantthe closed set of legal statesmakes illegal states unrepresentable
errora named value with contexta string error can only be logged, not handled

A — the happy path

loadOrder → checkPolicy → recordRefund → publishEvent

That graph is the program structure. The rule with teeth: A must read top to bottom with no error handling interleaved.

E — where it breaks

policywhenmust also record
↻ retrytransient: timeout, rate limit, lock conflictthe bound — attempts, backoff, budget
⤵ fallbackrecoverable: default, cache, degraded answerwhat the caller loses
↑ propagatethe caller's problemthe vocabulary it maps into
✷ dieinvariant violated, programmer errornothing — do not catch it

An unbounded retry is an outage amplifier, not resilience. A failure handled by accident is the same as unhandled.

EACH LAYER SCOPES ITS OWN E

repository      service          handler           transport
SqlError    →   DatabaseError →  RefundRejected →  422 + code
SqlTimeout  →   DatabaseError →  Unavailable    →  503
                PolicyDenied  →  RefundRejected →  422 + code
                (unmapped)    →  die            →  500 + alert

A layer enumerates what it received and maps it into its own words. Two failures to watch for: leaking, a driver error reaching a caller unchanged so it couples to your storage engine; and collapsing, two errors the caller must distinguish arriving as one.

R — what the node needs

Complete this sentence for every dependency: we cannot do this without that. A hidden R is the core failure — a global, a singleton, the wall clock, a random source, an env read mid-function. Invisible in the signature, and precisely why a node cannot be tested without mocking the world.

production                  test
handler                     handler
 → RefundService             → RefundService
   → PostgresOrderRepo         → InMemoryOrderRepo
   → HttpLedgerClient          → StubLedgerClient
   → time.Now                  → fixedClock

Same graph shape, same A, same E possible — only what sits behind R changes. Which doubles as a design check: if you have to mock the world to test one node, the node is doing too much.

cardinality, boundary, layers, scope

CARDINALITY

one needs nothing further. many requires deciding ordering, backpressure, completion, and what a mid-stream failure means — "the tenth item failed after nine committed" has no safe default. time_bounded requires a cache key, a TTL, and whether concurrent identical lookups deduplicate. A many node implemented as one is the bug where only the first page is ever processed.

BOUNDARY

One parse point at the edge, with one definition serving as type, validator and transformer. Validation appearing inside a node means either the boundary is not doing its job or a caller is bypassing it.

LAYERS

Retry, timeout, logging, tracing, metrics, caching, auth — composed outside the node so its graph is unchanged. The test: could you delete the logging without touching the happy path?

SCOPE

Every acquired resource needs release guaranteed on every exit path including error and cancellation. Cleanup is a language construct, not a convention.

07 · THE GATES IN FULL

Requirement gate

idcheck
Q1an acceptance check exists, committed as a spec at the chosen altitude
Q2it runs and is red for the intended reason, with the failure recorded
Q3every assumed ambiguity has an assertion, or is escalated as untestable
Q4deterministic: time pinned, data seeded, selectors stable, no sleeps
Q5the command is in the check manifest, so the loop re-runs it without improvising

The harness follows the altitude, never preference: a user-visible flow gets a browser check, an HTTP contract an API check, a command a CLI check, an event a consumer check, a pipeline a real run, a migration a seeded database. Two altitudes for one requirement means it is two requirements.

G1behavior has a verdict, a purpose it serves, and an owning role from role_routingtriage

Evaluated per behavior, not per node. A node with four behaviors passes four times, and may be implemented only up to the behaviors that passed. That is what makes the re-check pass work: when implementation reveals a behavior nobody predicted, it does not get written on the spot.

G8 catches the one people skip. A seam contract asserted only in prose fails the gate, because nothing will tell you when it stops being true.

08 · TRANSLATING THE REQUIREMENT

A PM's prose is neither searchable nor assignable. Translation happens first, and it is mined from what exists — the model is already in the codebase's table names, type names, test names and commit history, usually in an older dialect than the ticket. A glossary the code does not share is just a second vocabulary to maintain.

THE GLOSSARY HAS FOUR COLUMNS BECAUSE THE DISAGREEMENTS ARE THE POINT

domain termproduct sayscode saysdead aliases
Refundmoney backRefund, refund_recordsReversal, chargeback_v1
Ledger EntrytransactionLedgerEntryjournal_line
Refund Policyrefund rulesnothing — implicit—

Dead aliases are recorded deliberately: skipping them is the commonest reason a trace misses the node that matters. And a concept with no name in code lives scattered across whatever files happened to need it — which is exactly how rules end up inside application services. Naming it is often the actual work of the ticket.

Every behavior goes to one of two homes

"a refund may not exceed the remaining balance"
   → invariant     → the Order aggregate

"after a refund, write a ledger entry and email the customer"
   → sequence      → the RefundOrchestrator

"a refund over 10,000 needs manager approval"
   → invariant, but on what? Not on Order's balance.
   → a RefundPolicy concept is missing. Name it, then it has a home.

An application service's purpose reads as a sequence. If it reads as a rule, a rule has migrated into it. Threshold comparisons and status checks inside an application service, a process manager or a controller are almost always displaced invariants.

One transaction, one aggregate. If a behavior needs two to commit atomically, either the boundary is wrong or it is a policy: emit an event, handle it eventually, name the compensation.

Widening a purpose is not the agent's to grant. For a misplaced behaviour there are exactly two options available without a human: place it in a node whose purpose already covers it, or create a node whose purpose does. Widening an existing purpose is a third option requiring ratification — recorded with the current purpose, the proposed one, and what else the wider statement would then admit. An escape hatch reachable without approval is the path of least resistance, and it is how a purpose quietly becomes "whatever landed here".

09 · CROSSING TO OTHER SYSTEMS

The graph continues over HTTP, RPC, queues, databases and infrastructure config. A seam is a node — seam:http:POST /v2/refunds, seam:topic:refund.recorded, seam:table:orders — with a contract in five parts, of which usually only the first is written down anywhere.

partcovershides in
shaperequest, response, payload, columnsOpenAPI, proto, migration
errorsstatus codes, RPC codes, DLQ conditionsusually nowhere
translationhow errors map outward, and backusually nowhere
semanticsidempotency, ordering, delivery, timeoutsusually nowhere
authwho may call, with what scopegateway or mesh config

The four undocumented parts cause the outages. A consumer retrying a non-idempotent endpoint is not violating a written contract — it is violating one nobody wrote.

Relationship predicts blast radius, before any tracing

relationshiptheir change reachesso
anti-corruption layershallow — the ACL node onlytrace to the ACL and stop — it absorbs
published languageshallow — the artifact, then your adapterdiff the artifact
conformistdeep — your whole domainkeep tracing; widest blast radius
shared kerneldeep — both, bidirectionallythe only legitimate lockstep deploy
customer–suppliernegotiated — on their schedulea task-tier blocking edge
separate waysnone — by designa trace crossing here means a mistake

A seam to a foreign context with no ACL and no published language is the highest-risk shape available: you have taken on their model with no translation point, so every change of theirs is an unbounded change of yours. Worth raising even when the ticket did not ask.

Two asymmetries

Provider-side caller sets are unprovable. In-process, the compiler enumerates every caller. Across a published seam you get evidence, never proof — so stop chasing a complete upstream trace and make the contract compatible instead. Anything removed or narrowed is breaking, however few consumers were found.

Seam drift needs its own check. A seam can drift with no commit in your repo at all: the provider deployed, nothing here changed. Git cannot see that, so the seam records the provider version at trace time, and revalidation diffs the artifact, runs the contract test, or compares the deployed version.

DEPLOY ORDER IS A TABLE, NOT A JUDGMENT CALL

changeorder
additive providerprovider first — consumers cannot use what is not there
removalconsumer first — the provider cannot remove what is still called
in-place shape changenever — split into additive plus removal
new required fieldprovider accepts it optional first
stricter validationprovider last — it is a removal of tolerance
column add / dropmigration first / code first, migration later

The rollout window is the skipped part: both directions must hold. Old callers against the new provider, and new callers against the old one. The second is what breaks during a canary and during a rollback.

Every status is carried by its glyph and its word as well as its colour. Hue is never the only cue — use shapes only in the bar to drop colour entirely.

One tree, five tiers

Requirement, task, node chain, symbol, behaviors — indentation is call depth, not category. The tree is rooted at the entrypoint-most node reached, so it reads in the direction the system actually runs. The seed is marked ★ because it is where the search landed, not where the flow starts.

Depth labels restore direction

d-1 is a caller, d+1 a callee, signed relative to the seed. Past two levels of nesting, indentation alone stops telling you which way an edge points, and the sign puts it back.

Order markers are the edit plan

#1 #2 #3 are positions in the ordered change set. Deep nodes carry low numbers because callees go first — so a node numbered lower than its own parent is correct and expected, while a node numbered higher than something it depends on is a sequencing bug the shape makes visible. The tree plus the numbers is the whole plan; nothing else needs to state it.

A shared node is expanded once

Second and later parents get ↩ path (expanded above). Expanding twice doubles the tree and hides that the node is shared — and shared nodes are precisely the ones whose contract must not change casually. Cycles get ↺ and are never followed.

Detail goes where the motion is

levelshows
L0requirement only, with check results
L1requirements and tasks
L2the node tree with statuses — the default
L3adds symbols
L4adds behaviors, gates and channels

Default output is L2 across the tree with only the node in motion expanded to L4. A full L4 tree of a real trace is unreadable and buries the one node that matters.

Draw the changed subgraph, not the whole trace

Nodes that change, the path connecting them, and one hop of absorption frontier. Everything else traced and unaffected is omitted — not collapsed — behind a single line: ⊕ 14 nodes traced, unaffected (L2-full to show).

The distinction that matters: an absorbed node adjacent to a changing node is evidence of where the change stopped, so it stays drawn. An absorbed node three hops away is just something the trace ruled out, and it does not earn a line every time the graph prints. The absorbed set only grows, and re-printing it each turn teaches the reader to skim the whole thing. The evidence stays in the trace file, and L2-full draws everything when a reviewer asks why a node was ruled out.

Past a seam, keep nesting

Far-side nodes carry their service prefix and hang off the seam node, since the seam is the thing holding the contract. The graph spans services in one tree rather than stopping at the wire.

The artifact form of the same information goes to .design/<ref>.<task-slug>.graph.md — one per task — on every state write: context map, file graph, channel view, requirement→behavior→test coverage chain, deploy sequence.

A reversal is a new line, never an edit

A verdict that went no_change → change because a compiler error moved it is worth more than the verdict it replaced, so the log keeps both and the CLI refuses a reversal with no --why. The state says what was decided; the log says what decided it, and that is the part worth reading on the next ticket.

Each subcommand validates, appends one decision, re-folds and renders — so the status tree reaches the transcript on every change without anyone electing to print it.

What it refuses is the point: a verdict on a node with no purpose, a no_change with no stop reason, a reversal with no reason, a gate with no observed red evidence, an invariant on an application service, and a close with requirements still open. A rule the CLI enforces is a rule that cannot be skipped under time pressure, which is the difference between a method and a suggestion.

A PostToolUse hook redraws the tree on any write under .design/, so the graph stays visible without being asked for.

Its question — does something already do this? — is the same one locate asks as prior art, which makes it a real fit rather than a bolt-on. And its ponytail: shortcut comments are exactly what this method calls accepted debt, so each is recorded in state with its upgrade path at finalize.

The conflict, and where the line falls

ponytail wants the shortest thing that works. The behaviour gate wants an annotated contract, one policy per break point, a single parse point, a structural release. These look opposed and are not:

PRECEDENCE

Minimality applies to the implementation. Specification is not negotiable. The smallest code satisfying every annotated behaviour is what both want.

So ponytail-review may propose deleting anything no behaviour claims — genuinely useful, and unclaimed code is a real finding. It may not delete an error policy, a boundary parse, a scoped release or a test. "No behaviour asked for this error handling" means the E annotation is missing, not that the handling is surplus.

What caveman may not compress

  • the status tree — it is the report, not commentary on it
  • gate verdicts and which check failed; a compressed refusal is an unclear one
  • red evidence: command, exit status, failure message, verbatim
  • the expected-versus-observed line on a red check
  • a falsified assumption reported back to you — the loop's highest-value output, and the thing most damaged by terseness
  • anything escalated for a human decision

Compression on narration is safe here for a structural reason: caveman leaves code blocks and error messages exactly as written, and all of the above except the prose is a block.

One honest note: in ponytail's own agentic benchmark, caveman measured slightly above the no-skill baseline on tokens, cost and time, because agentic cost is dominated by file reading and tool calls rather than prose. Install it because the padding annoys you, not as a cost strategy.

instead ofthe rule
a fan-in thresholdadditive deltas never expand upstream; breaking deltas are enumerated with a compiler or a coverage run; unenumerable ones are not broken in place. Count affects drawing only
a depth limitupstream ends at the flow's entrypoint, downstream at a leaf or opaque seam. Three transform-free hops are a pass-through to collapse. Still propagating at the entrypoint is a finding, not a limit
